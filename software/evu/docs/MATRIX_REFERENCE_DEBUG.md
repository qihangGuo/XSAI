# Matrix Reference Not Ready

This diagnosis applies to `run_quanti8mma_evu.log`, generated by the EMU built
on October 22, 2026 at 13:59:21. It does not assume that the server's reference
library matches the current local NEMU sources.

## First Failure

The first error occurs at cycle 30432, on matrix result row 0, column 0:

```text
reason=not-ready launch_pc=0x800003ee active=1 ready=0
row=0 col=0 dim=128 bytes=32 mask=0xff
REF producer hooks: zero_mask=0x0 load_mask=0x3 mma_count=0
```

`not-ready` is returned before comparing matrix data. NEMU has accepted the
launch and observed both input loads, but has not recorded an accumulator
zero or MMA. This is a missing reference result, rather than evidence of
incorrect DUT matrix arithmetic. `checked_matrix_beats=0` is consistent with
aborting at the first result beat.

`build/quanti8mma_evu_example-riscv64-xs.txt` and the commit trace identify:

| PC | Operation |

| `0x800003ee` | `XV_LAUNCH_FP32` |

| `0x800003fa` | load input tile 0 |
| `0x80000406` | load input tile 1 |
| `0x8000040a` | `mmacc acc0, tr1, tr0` |
| `0x8000040e` / `0x80000414` | release / acquire |
| `0x80000418` / `0x8000041c` | EVU WAIT / FENCE |

These instructions have committed before the mismatch; the logged REF PC is
`0x80000420`. The final `ABORT at pc=0x80000392` is not the location of the
matrix mismatch: that address disassembles to an earlier scalar output
initialization store.

The DUT's first eight FP32 words decode to:

```text
bits:   43000000 42800000 00000000 c2800000 c3000000 43000000 42800000 00000000
values: 128      64       0        -64      -128     128      64       0
```

For the first launch's unit scales, K=64 and the test's periodic INT8 inputs,
these are the expected first eight outputs. This confirms only this beat,
not the remaining stream, address generation or second launch.

## Likely Cause And Server Checks

Current local `NEMU/src/isa/riscv64/instr/ame/mcompute.h` calls
`evu_matrix_zero()` before the `CONFIG_SHARE_REF` exclusion and calls
`evu_matrix_mma()` after that exclusion. Thus the hooks execute even when the
ordinary AME arithmetic is omitted in the shared reference. They should
produce `zero_mask=0x10 load_mask=0x3 mma_count=1` for this launch and make the
matrix reference ready.

The log instead matches a library with working load hooks but missing zero
and MMA hooks. The leading explanations are incomplete source synchronization,
an interpreter object built before the header changes, or a different library
being loaded. The log alone cannot select among them. Verify the server's
exact checkout and library; do not change matrix arithmetic on this evidence.


Check the surrounding `#ifndef CONFIG_SHARE_REF` boundaries as well as the
presence of the calls. Synchronizing only `instr/evu/matrix.c` supplies new
diagnostics but cannot add missing interpreter calls in `mcompute.h`.

The helper cleans/rebuilds NEMU and prints the tested library's SHA256. Require
all three native launches and 6144 result beats to pass, then run EMU with
that exact library path. If the native regression passes but EMU still reports
the same missing hooks, investigate reference instruction skipping/integration
and confirm the loaded binary before concluding that this is a DUT failure.
No matrix implementation or NEMU source was changed for this diagnosis.
